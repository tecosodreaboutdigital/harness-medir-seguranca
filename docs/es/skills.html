Skills para agentes

El harness, escrito para que la máquina lo siga

Una skill no es un atajo para darle más poder al agente. Es el harness en una forma que él puede seguir: qué puede hacer, qué nunca hace y quién confirma.

Formato e instalación

Las skills siguen el formato abierto Agent Skills: una carpeta por skill, con un archivo SKILL.md que empieza con name y description en YAML. Cualquier agente compatible con ese formato puede cargarlas. Las instrucciones están en portugués, con un resumen corto en inglés al inicio de cada archivo.

  1. Abra la carpeta skills/ del repositorio y lea el SKILL.md completo. Una skill que no leyó es una instrucción desconocida funcionando dentro de su agente.
  2. Copie la carpeta de la skill al directorio de skills de su agente (en Claude Code, por ejemplo, .claude/skills/ en el proyecto).
  3. Pruebe con una alerta ficticia antes de usar cualquier dato real.
Sección obligatoria

Toda skill de este repositorio tiene una sección de harness con tres líneas: qué puede hacer, qué nunca hace y quién confirma. Una skill sin esa sección no entra.

saude-da-operacao

Paso Inspeccionar · sello de integridad del dato

Las señales de salud (Zabbix, SNMP, ping, HTTP, grabación, reloj) se vuelven un sello en cada número y cada alerta: íntegro, estimado, atrasado o sin dato. Gana el peor sello, el cero solo aparece con sello íntegro, y una falla de infraestructura nunca aparece como "no pasó nada".

Puedeleer señales, calcular el sello, alertar, abrir un ticket de mantenimiento
Nuncareiniciar equipos, silenciar problemas, mostrar cero sin datos
Quién confirmael operador lo encamina; mantenimiento confirma causa y reparación

mcp-central

Pasos Equipar y Delegar · diseño de servidor MCP

Documento de diseño de un servidor MCP con tres herramientas: consultar_alerta (leer una alerta), abrir_chamado (abrir un ticket) y pedir_trecho_de_video (pedir un tramo de video). Revisión de seguridad de las integraciones

Las skills que tocan sistemas (grabación, control de acceso, salud de la operación y el servidor MCP) comparten la misma revisión mínima. Cada "no" es un pendiente con responsable, antes de encender.

  • Autenticación en todo canal; nada anónimo.
  • Mínimo privilegio: la credencial solo lee lo que el caso necesita.
  • Solo lectura por defecto; escribir en un sistema de terceros es una decisión registrada y sube el nivel.
  • Secretos fuera del repositorio, en variables de entorno o en un gestor de secretos, con rotación.
  • Logs sin datos personales: id, tipo, hora y resultado; nunca imágenes, rostros, placas ni nombres.
  • Límite de tasa y de tamaño, con errores que dicen qué hacer.
  • Protección contra repetición en webhooks: HMAC-SHA256 sobre timestamp y cuerpo, ventana corta, rechazo de ids repetidos.

Todos los ejemplos usan hosts exemplo.local, secretos de prueba leídos de variables de entorno y ningún dato de sistemas reales.
